## 一、项目概述

本系统是一个面向超市日常运营的**商品进销存管理后台**，覆盖商品、库存、销售三大核心业务链路，辅以分类、供应商、系统用户与运营仪表盘。

前端已完整实现（登录、商品档案、商品分类、供应商、入库、出入库流水、库存统计、收银开单、销售记录、销售统计、用户管理、个人中心、运营总览共 13 个页面），当前以 mock 数据演示。**后端需按本文档实现接口，使前端从 mock 切换到真实数据。**

### 1.1 业务闭环

系统的核心业务是「进 → 销 → 存」的完整闭环，所有操作最终反映在**商品库存**与**出入库流水**两个核心数据上：

```
采购入库 ──→ 库存增加 ──→ 销售出库 ──→ 库存减少
                    │                │
                    └──── 出入库流水（每一笔变动自动留痕）────┘
                              │
              （退货回补库存 / 出库报损 / 销售作废均走流水）
```

### 1.2 后端职责边界（关键）

后端必须承担以下**前端不做、也不该做**的核心职责：

1. **库存充足性校验**：出库、销售结账时判断库存是否足够，不足则拒绝并返回明确错误。
2. **实际库存增减**：入库加库存、出库减库存、销售扣库存、退货回补库存。
3. **出入库流水自动生成**：每次库存变动，后端自动写入流水记录（含变动前后库存量）。
4. **删除约束**：分类/供应商被商品引用时拦截删除；商品存在业务记录时拦截删除。
5. **角色鉴权**：前端隐藏菜单不等于安全，后端必须在每个受控接口做二次鉴权。

## 二、技术架构要求

| 项 | 要求 |
|----|------|
| 运行时 | Node.js（建议 ≥ 16） |
| Web 框架 | Express |
| 数据库 | MySQL（建议 8.x，InnoDB 引擎，utf8mb4 字符集） |
| 鉴权 | JWT（token 携带 userId、role） |
| 密码存储 | 加密存储（bcrypt 等），**禁止明文** |
| 事务 | 库存/销售业务必须使用 MySQL 事务 |
| 接口风格 | RESTful，统一前缀 `/api` |
| 响应格式 | 统一 `{ code, msg, data }`，字段 camelCase |
后端采用 MVC 架构模式进行开发，使用 Node.js+Express 搭建服务。Model 模型层封装数据库 SQL 操作，负责数据持久化；Controller 控制器处理业务逻辑、参数校验、事务控制；Router 路由层负责请求分发。前后端分离架构，后端只输出 JSON 数据，视图层交由 Vue3 前端实现。使用 JWT 完成身份认证，区分管理员和操作员角色权限；对于销售开单、库存盘点这类需要保证数据一致性的业务，采用 MySQL 事务，防止库存与单据数据不一致。
### 2.1 项目初始化约定

- 数据库初始化时需预置**基础数据**（对应前端 mock 数据）：
  - 5 个商品分类（饮料乳品/休闲零食/粮油调味/日用百货/生鲜果蔬）
  - 5 家供应商
  - 至少 16 个商品档案
  - 管理员账号 `admin`（初始密码 123456）与若干演示用户
- 预置数据可参考前端 `src/views/*/mock.js` 中的字段值，保证前端切换后展示效果一致。

## 三、角色与权限体系

### 3.1 双字段设计

用户表包含两个相关字段，**职责分离**：

| 字段 | 取值 | 用途 |
|------|------|------|
| `role` | `admin` / `operator` | 后端鉴权判定 |
| `position` | 管理员 / 仓管 / 收银员 / 后勤 / 采购 / 会计 | 前端展示与职位管理 |

**映射规则（后端维护，写入/更新时自动判定）：**

```
position === '管理员'  →  role = 'admin'
其余所有职位           →  role = 'operator'
```

### 3.2 权限矩阵

| 功能 | admin（管理员） | operator（操作员） |
|------|:---:|:---:|
| 登录 / 查看本人资料 / 修改密码 | ✅ | ✅ |
| 商品档案、分类、供应商 **查看** | ✅ | ✅ |
| 商品档案、分类、供应商 **增删改** | ✅ | ❌ |
| 入库 / 出库 | ✅ | ✅ |
| 销售结账 | ✅ | ✅ |
| 销售退货 / 作废 | ✅ | ❌ |
| 用户管理（列表/增删改/重置密码） | ✅ | ❌ |
| 运营仪表盘 / 各类统计 | ✅ | ✅ |

> **后端必须按此矩阵在接口层做鉴权**（401 未登录 / 403 无权限），不能只依赖前端隐藏按钮。

## 五、各模块功能需求

### 5.1 用户模块

**功能点：** 登录、退出、获取当前用户信息、修改密码、更新个人资料、用户列表、新增/编辑/删除用户、重置密码。

**业务规则：**

1. **登录**：校验账号密码 → 校验用户是否启用（禁用则拒绝）→ 返回 token（含 userId、role）、role、position、username。
2. **个人资料更新**（员工在个人中心自助修改）：
   - 可改：头像、姓名、性别、生日、手机号、身份证号、住址、个人简介。
   - **不可改**（敏感字段，仅管理员在用户管理页可改）：工资 salary、入职时间 joinDate、职位 position、角色 role。后端需忽略这些字段的传值。
3. **用户管理**（仅管理员）：
   - 新增用户：用户名唯一（3-20 位字母/数字/下划线），初始密码默认 `123456`，role 由 position 自动映射。
   - 编辑用户：用户名**不可改**，position 变化时 role 需同步重新映射。
   - 删除用户：禁止删除自己、禁止删除系统内置管理员。
   - 重置密码：管理员为指定用户设置新密码（≥6 位）。
4. 用户列表**不得返回 password 字段**。

---

### 5.2 商品分类模块

**功能点：** 分类列表（全量）、新增、编辑、删除。

**业务规则：**

1. 分类名称唯一。
2. 分类有 `colorToken`（图表色标，取值 `--chart-1` ~ `--chart-5` 及扩展预留），供前端图表配色。
3. 分类有 `sort`（排序值，越小越靠前）与 `status`（启用/禁用）。
4. **删除约束**：分类下存在商品时禁止删除，返回「该分类下存在商品，无法删除」。

---

### 5.3 商品档案模块

**功能点：** 商品列表（分页+筛选）、商品详情、新增、编辑、删除。

**业务规则：**

1. 商品条码 `productCode` 唯一；为空时后端自动生成（`690` 前缀 + 10 位序号）。
2. 价格校验：销售价必须 > 0，进货价 ≥ 0。
3. **库存状态自动联动**：库存数 `stockNum = 0` 时，商品自动置为「下架」（status=0）。
4. **库存预警**：`stockNum < warnNum` 视为预警（前端表格显示预警标签，供运营关注）。
5. 商品列表需关联返回 `categoryName`、`supplierName`。
6. **删除约束**：商品存在流水或销售明细记录时禁止删除（建议软删除）。

---

### 5.4 供应商模块

**功能点：** 供应商列表（分页）、下拉选项、新增、编辑、删除。

**业务规则：**

1. 供应商名称唯一。
2. 提供「下拉选项」精简接口（仅 id + 名称），供入库单和商品表单选择。
3. **删除约束**：供应商被商品引用时禁止删除，返回「该供应商下存在关联商品，无法删除」。

---

### 5.5 库存管理模块（核心）

**功能点：** 入库明细、提交入库、出库明细、提交出库、预警商品、出入库流水、库存统计。

#### 5.5.1 入库

- 操作者选择商品 + 数量（>0）+ 可选供应商/单价/备注。
- **事务**：商品 `stock_num += quantity`，同时写入入库流水（changeType=1，记录 beforeNum/afterNum）。
- 若商品原为缺货下架，入库后可自动上架（status=1）。

#### 5.5.2 出库

- 操作者选择商品 + 数量（>0）+ 可选备注（用于报损、领用等场景）。
- **库存不足校验**：`quantity > stock_num` 时拒绝，返回「出库数量大于当前库存」，**不产生任何数据变更**。
- **事务**：商品 `stock_num -= quantity`，同时写入出库流水（changeType=2，记录 beforeNum/afterNum）。

#### 5.5.3 出入库流水

- 只读查询（分页 + 筛选），按时间倒序。
- 每条流水必须包含：商品、类型（入库/出库）、变动数量、**变动前库存、变动后库存**、操作人、时间、备注。

#### 5.5.4 库存预警

- 预警判定：`stockNum <= 0` → 已缺货（warnStatus=2）；`0 < stockNum < warnNum` → 低于预警值（warnStatus=1）。
- 按库存升序返回（缺货在前）。

#### 5.5.5 库存统计

- 实时聚合返回：库存总量、预警商品数、缺货商品数、待盘点商品数、库存总价值（Σ 进货价 × 库存）。

---

### 5.6 销售管理模块（核心）

**功能点：** 销售记录列表、销售记录详情、提交销售（收银结账）、销售退货、销售作废、销售明细按商品查询、销售统计聚合。

#### 5.6.1 提交销售（收银结账）

这是系统**最复杂的写操作**，必须在单个事务内完成，涉及 4 张表：

**事务流程：**

1. **前置校验**（任一项失败则整个事务回滚，不扣任何库存）：
   - 商品列表非空；
   - 每个商品存在且「在售」（status=1）；
   - 每个商品库存充足（quantity ≤ stockNum）。
2. 生成销售单号：`XS` + `yyyymmdd` + `-` + 3 位当日序号（如 `XS20261011-001`）。
3. 写入销售记录 `sale_record` 与销售明细 `sale_item`（明细含商品名、分类名、成本价的**冗余快照**，用于历史单据不受商品后续改名/改价影响）。
4. 逐商品扣减库存 `stock_num -= quantity`。
5. 逐商品写入出库流水 `stock_log`（changeType=2）。
6. 汇总 `totalQuantity`（总件数）与 `totalAmount`（总金额 = Σ 销售价 × 数量，保留两位小数）。

**金额口径：** 前端可能传 `salePrice`（收银改价），未传则取商品当前 `sale_price`；成本价取商品 `cost_price`（用于毛利统计）。

#### 5.6.2 销售退货（整单退款）

**事务流程：**

1. 校验单据状态：已退货/已作废则拒绝。
2. 单据置为「已退货」（status=2）。
3. 逐商品回补库存 `stock_num += quantity`。
4. 逐商品写入入库流水（changeType=1，备注注明「销售退货」）。

#### 5.6.3 销售作废

- 仅将单据置为「已作废」（status=3），**不恢复库存**（用于误录冲正场景）。
- 已退货/已作废的单据不可再作废。

#### 5.6.4 销售统计（后端聚合）

- 按日期区间（默认近 7 天）、分类、商品名筛选，后端一次返回：
  - 汇总：总件数、总金额、总成本、总毛利；
  - 每日趋势：区间内每天的销售额/成本/毛利（无销售日为 0）；
  - 分类占比：各分类销售额（降序）；
  - 商品统计：各商品的销量/金额/成本/毛利/毛利率（降序）。
- **口径**：仅统计「正常」单据（status=1），已退货/已作废不计入。

---

### 5.7 运营仪表盘模块（只读统计）

**功能点：** 运营总览指标、近 N 日销售趋势、库存余量 TOP5、各分类库存占比、热销商品 TOP5。

**业务规则：**

1. **运营总览**：一次返回首页所需全部指标（今日/本月销售额与利润及其环比、迷你趋势线、本月收货量、商品种类数、预警数、待盘点数）。
2. **热销 TOP5**：按售出数量降序取前 5（区间可取近 30 天）。
3. **库存 TOP5**：按当前库存降序取前 5。
4. 所有统计**只统计「正常」单据**，与销售统计口径一致。

## 六、核心业务规则汇总（务必遵守）

### 6.1 事务强制清单

以下操作**必须**在单个 MySQL 事务内完成，保证「库存 + 流水」的原子一致性：

| 操作 | 库存变化 | 流水 | 附加 |
|------|----------|------|------|
| 提交入库 | stock_num +N | changeType=1 | 缺货可自动上架 |
| 提交出库 | stock_num -N | changeType=2 | 先校验库存充足 |
| 提交销售 | stock_num -N（逐项） | changeType=2（逐项） | 写 sale_record + sale_item |
| 销售退货 | stock_num +N（逐项） | changeType=1（逐项） | 单据置为已退货 |
| 销售作废 | 不变 | 不生成 | 单据置为已作废 |

### 6.2 库存不足处理

- 出库/销售结账时库存不足，**必须拒绝**，返回明确错误文案（如「出库数量大于当前库存」「商品 xxx 库存不足」），且**不得产生任何部分扣减**。

### 6.3 单号/条码生成规则

- 销售单号：`XS` + `yyyyMMdd` + `-` + 3 位当日递增序号，需保证当日唯一、不重复。
- 商品条码：前端留空时后端生成 `690` + 10 位序号，需保证全局唯一。

### 6.4 流水完整性

- 每次库存变动**必须**生成流水，流水须记录**变动前库存（beforeNum）与变动后库存（afterNum）**，保证库存账可追溯。
- 流水为历史记录，**不允许修改、删除**。

### 6.5 数据一致性（金额）

- 金额统一 `DECIMAL` 存储，计算保留两位小数，避免浮点误差。
- 销售明细的金额 = 销售价 × 数量；毛利 = 金额 - 成本价 × 数量。

## 七、安全与鉴权要求

1. **Token 鉴权**：除登录外所有接口需校验 token；无效/过期返回 401。
2. **角色鉴权**：管理员专属接口（用户管理、销售退货/作废、增删改）需校验 `role === 'admin'`，否则返回 403。
3. **密码安全**：bcrypt 等加密存储，禁止明文；接口任何返回都不得包含 password。
4. **越权防护**：操作者字段（operator）从 token 解析，**不接受前端传值**，防止伪造操作人。
5. **输入校验**：所有写接口后端必须做参数校验（类型、范围、格式），不能信任前端。

## 十、对接提示（给后端）

1. **先读 `api.md`**：本文档是「业务需求」，`api.md` 是「接口契约」，字段结构、URL、入参出参以 `api.md` 为准。
2. **前端已就绪**：前端 `src/api/modules/*.js` 已按 `api.md` 的 URL 和参数封装好，后端接口的 URL、字段名、响应体必须严格对齐，否则前端对接会失败。
3. **响应体格式**：必须 `{ code, msg, data }`，字段 camelCase。前端响应拦截器会解包 `data`，业务失败（code≠200）自动弹 `msg`。
4. **角色字段**：登录接口务必同时返回 `role`（英文）与 `position`（中文），前端用 `position` 判断菜单权限。
5. **联调顺序建议**：先用户/登录 → 商品/分类/供应商 → 库存（出入库）→ 销售 → 仪表盘统计。

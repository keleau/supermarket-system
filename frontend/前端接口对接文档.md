## 二、全局约定（必读）

### 2.1 统一响应体

**所有接口**（包括出错）HTTP 状态码恒为 `200`，业务结果一律由响应体内的 `code` 表达：

```json
{
  "code": 200,
  "msg": "success",
  "data": {}
}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `code` | number | `200` 成功；`400` 参数/业务错误；`401` 未登录或登录已失效；`403` 无权限；`404` 接口不存在；`500` 服务异常 |
| `msg` | string | **可直接展示给用户的文案**，出错时直接 `message.error(msg)` 即可 |
| `data` | any | 业务数据，失败时为 `null` |

> ⚠️ **这是最容易踩的坑**：不要用 `axios` 的 `error` 分支判断失败。后端故意不返回 4xx/5xx，否则 `msg` 拿不到。判断成败**必须**看 `res.data.code`。

### 2.2 鉴权方式

除 `POST /api/user/login` 与 `GET /api/health` 外，**所有接口都必须带 token**：

```
Authorization: Bearer <token>
```

- token 由登录接口返回，有效期 **24 小时**（`.env` 的 `JWT_EXPIRES_IN` 可改）。
- token 载荷含 `userId / username / role / position / realName`，**前端不需要再解 JWT**，登录接口的 `data` 里已直接给出 `role`、`position`、`realName`、`avatar`。
- 退出登录后 token 进入服务端黑名单，**立即失效**；前端应同时清空本地存储并跳转登录页。
- 收到 `code === 401` 时统一处理：清 token → 跳登录页 → 提示 `msg`。

### 2.3 分页约定

**请求**（query 参数，所有列表接口通用）：

| 参数 | 类型 | 默认值 | 约束 |
| --- | --- | --- | --- |
| `pageNum` | number | `1` | 最小 1 |
| `pageSize` | number | `10` | 1 ~ 200，超出自动截断 |

**响应** `data` 结构：

```json
{
  "list": [],
  "total": 26,
  "pageNum": 1,
  "pageSize": 10
}
```

> 注意：`pageNum` / `pageSize` 在 `data` 内部，不在顶层。

### 2.4 参数传递位置

| 场景 | 位置 |
| --- | --- |
| 列表/查询条件 | **query**（`?a=1&b=2`） |
| 新增 / 编辑 / 业务提交 | **body**（JSON） |
| 删除 | **路径参数**（`/api/product/12`），无 body |

> 编辑接口（`PUT`）的 `id` 放在 **body** 里，不是路径参数。删除接口（`DELETE`）的 `id` 才是路径参数。

### 2.5 日期与时间约定

| 场景 | 格式 | 说明 |
| --- | --- | --- |
| 传入 `startTime` / `endTime` | `YYYY-MM-DD` 或 `YYYY-MM-DD HH:mm:ss` | 只传日期时，`startTime` 自动补 `00:00:00`，`endTime` 自动补 `23:59:59` |
| 出生日期 / 入职日期 | `YYYY-MM-DD` | |
| 返回的 `createTime` | `YYYY-MM-DD HH:mm:ss` | 直接展示即可 |
| 统计类返回的 `date` | `YYYY-MM-DD` | 用于图表 x 轴 |
| 仪表盘趋势返回的 `date` | `MM-DD` | 已格式化，直接展示 |

### 2.6 数值类型提醒

后端金额字段统一**保留 2 位小数**并返回 number。前端展示时用 `Number(x).toFixed(2)`；提交时直接传 number 即可，后端会自行 `round2` 兜底。

`id` 为 BIGINT，**统一按数字处理**即可（演示数据量级安全）。

## 三、请求封装示例（Axios）

这是「正式接入」的第一步，建议放在 `src/utils/request.js`，后续所有页面统一调用。

```js
import axios from 'axios';
import { ElMessage } from 'element-plus';
import router from '@/router';

const request = axios.create({
  baseURL: 'http://localhost:3000/api',
  timeout: 15000,
});

/* ---------- 请求拦截：自动挂 token ---------- */
request.interceptors.request.use((config) => {
  const token = localStorage.getItem('token');
  if (token) config.headers.Authorization = `Bearer ${token}`;
  return config;
});

/* ---------- 响应拦截：按 body.code 解包 ---------- */
request.interceptors.response.use(
  (response) => {
    const { code, msg, data } = response.data;

    if (code === 200) return data;        // 成功：直接返回 data，页面少写一层

    if (code === 401) {                   // 登录失效
      localStorage.clear();
      router.replace('/login');
    }

    ElMessage.error(msg || '操作失败');
    return Promise.reject(new Error(msg));
  },
  (error) => {                            // 网络层异常（断网、超时、后端未启动）
    ElMessage.error('网络异常，请检查后端服务是否已启动');
    return Promise.reject(error);
  }
);

export default request;
```

**用法**（页面里非常干净）：

```js
import request from '@/utils/request';

// 分页列表
const { list, total } = await request.get('/product/list', {
  params: { pageNum: 1, pageSize: 10, productName: '可乐' },
});

// 新增
await request.post('/product', form);

// 编辑（id 在 body）
await request.put('/product', { id: 3, ...form });

// 删除（id 在路径）
await request.delete(`/product/${id}`);
```

建议再按模块封装一层 API 文件（`src/api/product.js` 等），页面不直接写 URL。

## 四、全局枚举字典（页面共用）

> **这一节是实现「各页面数据互通」的关键**：同一套枚举必须在所有页面共用，否则商品列表显示「在售」、库存页显示「1」，数据就对不上了。建议放在 `src/constants/dict.js` 全局引用。

### 4.1 用户职位 / 角色

```js
export const POSITIONS = ['管理员', '仓管', '收银员', '后勤', '采购', '会计'];

// 职位 → 角色 由后端自动映射，前端不要传 role
// 管理员 → admin，其余 → operator
export const ROLE_MAP = { 管理员: 'admin' };
```

### 4.2 通用状态（分类 / 用户）

| 值 | 含义 |
| --- | --- |
| `1` | 启用 |
| `0` | 禁用 |

### 4.3 商品状态

| 值 | 含义 | 备注 |
| --- | --- | --- |
| `1` | 在售 | |
| `0` | 下架 | **库存为 0 时后端会自动置为 0** |

### 4.4 出入库类型 `changeType`

| 值 | 含义 |
| --- | --- |
| `1` | 入库 |
| `2` | 出库 |

### 4.4.1 流水业务类型 `bizType`

`changeType` 只说明入/出，`bizType` 说明这笔库存为什么变：

| 值 | 含义 |
| --- | --- |
| `1` | 采购入库 |
| `2` | 销售出库 |
| `3` | 销售退货 |
| `4` | 盘点盘盈 |
| `5` | 盘点盘亏 |
| `6` | 期初入库 |
| `7` | 手工调整 |
| `8` | 作废回补 |

> 流水列表同时返回 `bizTypeName`（中文），前端直接展示即可。商品首次入库自动标记为「期初入库」，后续入库标记为「采购入库」。

### 4.5 库存预警状态 `warnStatus`

| 值 | 含义 | 判定规则 |
| --- | --- | --- |
| `1` | 库存偏低 | `0 < stockNum < warnNum` |
| `2` | 已缺货 | `stockNum <= 0` |

### 4.6 销售单状态

| 值 | 含义 | 是否计入统计 |
| --- | --- | --- |
| `1` | 正常 | ✅ 计入 |
| `2` | 已退货 | ❌ 不计入 |
| `3` | 已作废 | ❌ 不计入 |

> 所有销售额 / 毛利 / 趋势统计**只统计 `status = 1`** 的单据。

### 4.7 支付方式 `payType`

后端仅校验取值范围 `1 ~ 4`，**语义由前后端共同约定**，建议前后端对齐为：

| 值 | 建议含义 |
| --- | --- |
| `1` | 现金 |
| `2` | 微信 |
| `3` | 支付宝 |
| `4` | 银行卡 |

### 4.8 采购单状态 `status`

| 值 | 含义 | 可操作 |
| --- | --- | --- |
| `0` | 草稿 | 编辑、提交、取消 |
| `1` | 已提交 | 收货、取消 |
| `2` | 已入库 | 登记付款 |
| `3` | 已取消 | 无 |

### 4.9 采购付款状态 `payStatus`

| 值 | 含义 | 判定规则 |
| --- | --- | --- |
| `0` | 未付款 | `status = 2` 且 `paidAmount = 0` |
| `1` | 部分付款 | `0 < paidAmount < payableAmount` |
| `2` | 已付清 | `paidAmount >= payableAmount` |

> 草稿和已提交的采购单 `payStatus` 也为 `0`，前端只在 `status = 2` 时展示付款状态。

### 4.10 销售退货单状态 `status`

| 值 | 含义 | 可操作 |
| --- | --- | --- |
| `0` | 待确认 | 管理员确认/拒绝；申请人或管理员取消 |
| `1` | 已确认 | 已回补库存，原销售单变为已退货 |
| `2` | 已拒绝 | 原销售单保持正常 |
| `3` | 已取消 | 原销售单保持正常 |

> 整单退货：一张销售单最多存在一张「待确认 / 已确认」的退货单；被拒绝或取消后可以重新申请。

### 5.2 商品分类 `/api/category`

#### 🔑 GET `/api/category/list` 分类全量列表

**无分页**，返回数组，按 `sort` 升序：

```json
[
  {
    "id": 1,
    "name": "饮料乳品",
    "colorToken": "var(--chart-1)",
    "description": "矿泉水、乳制品、碳酸饮料等",
    "sort": 1,
    "status": 1,
    "createTime": "2026-10-13 10:00:00"
```

#### 👑 POST `/api/sale/record/void` 销售作废（仅管理员）

| 字段 | 类型 | 必填 |
| --- | --- | --- |
| `saleNo` | string | ✅ |

- **回补库存**，并逐商品写入 `bizType=8` 的「作废回补」入库流水。
- 原单状态改为 `3`（已作废），退出营收统计。
- 该单下待确认的退货申请会一并取消，避免二次回补。
- 已退货（`2`）或已作废（`3`）的单据不能再次作废。

> **退货 vs 作废 的区别**：退货是「顾客真的把货退回来了」→ 先申请、管理员确认后回补库存并冲减营收；作废是「单据录错了」→ 管理员直接作废、回补库存并取消待确认退货。前端在按钮旁应给出这层说明，避免误操作。

## 七、跨页面数据联动说明

这一节解释**为什么各页面必须共享数据源与刷新机制**——后端把「库存」做成了唯一事实来源（single source of truth），一次业务操作会同时改变多个页面的数据。

### 7.1 库存是所有页面的公共依赖

```
                 ┌─────────────────────────────┐
                 │   product.stock_num / status │
                 │      （唯一事实来源）          │
                 └──────────────┬──────────────┘
        ┌───────────────┬───────┴───────┬────────────────┐
        ▼               ▼               ▼                ▼
   商品列表页      库存预警页      库存统计卡片      仪表盘首页
   (stockNum/     (warnStatus     (totalStock/    (warnProductCount/
    status)        1 / 2)          pending...)     pendingStockCount)
```

### 7.2 各操作的影响范围（前端据此决定刷新哪些页面）

| 操作 | 后端连带变更 | 受影响的前端数据 |
| --- | --- | --- |
| 入库 | 库存↑、写流水、**缺货商品自动上架** | 商品列表、入库明细、库存流水、预警列表、库存统计、仪表盘 overview |
| 出库 | 库存↓、写流水 | 商品列表、出库明细、库存流水、预警列表、库存统计、仪表盘 |
| 销售结账 | 库存↓、写出库流水、增销售单 | 销售记录、库存流水、商品列表、预警列表、库存统计、仪表盘、销售统计 |
| 销售退货申请 | 仅生成待确认退货单 | 退货单列表 |
| 销售退货确认 | 库存↑、写入库流水（bizType=3）、缺货商品自动上架、原单状态变 2 | 退货单、销售记录、商品列表、库存流水、预警列表、库存统计、仪表盘、销售统计 |
| 销售作废 | 库存↑、写作废回补流水（bizType=8）、取消待确认退货、原单状态变 3 | 销售记录、退货单、商品列表、库存流水、预警列表、库存统计、仪表盘、销售统计 |
| 采购收货 | 库存↑、写采购入库流水、更新加权成本、生成应付 | 采购单、商品列表、库存流水、预警列表、库存统计、仪表盘、供应商进货排行 |
| 商品增/改/删 | 商品档案变化 | 商品列表、商品下拉、库存统计、仪表盘 sku 数 |
| 分类增/改/删 | 分类档案变化 | 分类列表、商品列表 name 列、销售统计分类筛选 |

### 7.3 推荐的刷新策略

**方案 A（推荐，简单可靠）**：**不做跨页缓存**，每次进入页面 `onMounted` 重新拉数据。演示/毕设场景数据量小，完全够用。

**方案 B（体验更好）**：在 Pinia 维护一个全局 `dataVersion` 计数器，任何写操作成功后 `dataVersion++`，各数据页 `watch(dataVersion)` 决定是否重新请求。

```js
// stores/app.js
export const useAppStore = defineStore('app', {
  state: () => ({ dataVersion: 0 }),
  actions: {
    // 任何增删改 / 出入库 / 结账成功后调用
    refresh() { this.dataVersion += 1; },
  },
});
```

```js
// 页面内
const appStore = useAppStore();
watch(() => appStore.dataVersion, loadList);
```

### 7.4 必须共享的「字典数据」

以下数据**全站一份**，建议放 Pinia 缓存，避免每个页面各拉一次导致数据不一致：

| 数据 | 接口 | 使用页面 |
| --- | --- | --- |
| 分类列表 | `GET /api/category/list` | 商品管理、销售统计、库存、分类管理 |
| 供应商选项 | `GET /api/supplier/options` | 商品管理、入库、采购 |
| 商品下拉 | `GET /api/product/options` | 收银开单（仅在售）；入库/出库/采购传 `includeOffline=1` |

> 建议在 `categoryStore` / `supplierStore` / `productOptionStore` 中维护，并在 `appStore.dataVersion` 变化时失效重拉。

### 7.5 三个容易翻车的细节

1. **下单时的价格与成本是快照**。销售明细存的是下单瞬间的 `salePrice` 和当时加权平均成本 `costPrice`，商品后续改价或再次入库**不会**回溯影响历史单据。因此销售统计的毛利永远准确。前端展示历史单据时**不要**用当前商品售价去替换。

2. **库存为 0 会自动下架，入库/退货后会自动上架**。所以商品列表里「下架」有两种成因：手动下架、或库存为 0 被动下架。前端筛选「下架商品」时若想区分，需结合 `stockNum` 判断。

3. **统计口径只认 `status = 1`**。已退货（2）、已作废（3）的单据**不出现在任何销售统计里**，但**会出现在销售记录列表里**。所以「销售记录条数」和「统计里的订单数」对不上是正常的，UI 上要给出说明，避免被当成 bug。

## 八、前端状态管理建议

### 8.1 Pinia Store 划分

| Store | 存放内容 | 关键动作 |
| --- | --- | --- |
| `userStore` | `token`、`role`、`position`、`permissions`、`realName`、`avatar`、`username`、`phone` | `login()`、`logout()`、`fetchInfo()`、`isAdmin`、`can()`、`canAny()` |
| `dictStore` | `categories`、`supplierOptions`、`productOptions` | `loadCategories()`、`invalidate()` |
| `appStore` | `dataVersion` | `refresh()` |

```js
// userStore 里的权限判断（配合路由守卫）
getters: {
  isAdmin: (s) => s.role === 'admin',
  can: (s) => (permission) => s.permissions.includes('*') || s.permissions.includes(permission),
  canAny: (s) => (list) =>
    !list?.length || s.permissions.includes('*') || list.some((p) => s.permissions.includes(p)),
}
```

### 8.2 路由守卫要点

```js
router.beforeEach((to) => {
  const userStore = useUserStore();

  if (to.meta.public) return true;                 // 登录页放行

  if (!userStore.token) return '/login';           // 未登录

  // 仅管理员页面（用户管理、退货/作废入口）
  if (to.meta.adminOnly && !userStore.isAdmin) {
    ElMessage.error('无权限访问该页面');
    return false;
  }

  // 岗位权限页面（库存、收银、销售记录等）
  if (to.meta.permissions?.length && !userStore.canAny(to.meta.permissions)) {
    ElMessage.error('无权限访问该页面');
    return false;
  }
});
```

> 页面内按钮建议用 `v-if="userStore.can('stock:in')"` / `v-if="userStore.isAdmin"` 隐藏，**而不是禁用**——后端会返回 403，隐藏能减少无效请求。

### 8.3 `role` / `position` / `permissions` 的使用边界

- **`permissions`**（后端按岗位下发的权限码数组）→ 权限判断（路由守卫、菜单、按钮）。
- **`role`**（`admin` / `operator`）→ 管理员兜底判断；`admin` 拥有全部权限。
- **`position`**（中文职位）→ 只用于展示；后端据此生成 `permissions`，前端不要自行用 `position === '管理员'` 判断权限。

## 九、常见错误码与提示文案

| code | 触发场景 | 前端处理建议 |
| --- | --- | --- |
| `200` | 成功 | 正常渲染 `data` |
| `400` | 参数校验失败、业务规则不满足 | 直接 `ElMessage.error(msg)`，文案已是中文可读 |
| `401` | 未带 token / token 过期 / 已登出 | 清 token → 跳登录页 → 提示「登录已失效，请重新登录」 |
| `403` | 非管理员访问管理员接口 | 提示「无权限执行该操作」，并刷新页面权限状态 |
| `404` | 接口路径写错 | 开发期问题，检查 URL 拼接 |
| `500` | 服务端异常 | 提示「服务异常」，引导查看后端控制台日志 |

**高频业务文案**（可直接作为交互设计参考）：

| 文案 | 出处 | 前端预防 |
| --- | --- | --- |
| `出库数量大于当前库存` | 出库 | 提交前本地校验 |
| `商品 XXX 库存不足` | 销售结账 | 加购时用 options 的 `stockNum` 校验 |
| `商品 XXX 已下架` | 销售结账 | 只在售商品可选 |
| `该分类下存在商品，无法删除` | 分类删除 | 删除前提示 |
| `该商品存在业务记录，无法删除` | 商品删除 | 建议改为「下架」 |
| `该供应商下存在关联商品，无法删除` | 供应商删除 | 删除前提示 |
| `只有草稿状态的采购单可以修改` | 采购编辑 | 按 `status` 隐藏编辑按钮 |
| `只有已提交的采购单可以入库` | 采购收货 | 按 `status` 显示收货按钮 |
| `付款金额不能超过未付金额` | 采购付款 | 输入框 `max` 设为未付金额 |
| `该单据已退货` / `该单据已作废，无法退货` | 退货 | 按 `status` 禁用按钮 |
| `系统管理员不可删除` / `不能删除当前登录账号` | 用户删除 | 按规则禁用按钮 |
| `登录账号已存在` | 用户新增 | 失焦时不必单独查重，提交后提示即可 |
| `商品条码已存在` | 商品新增 | 同上；条码留空可自动生成 |
